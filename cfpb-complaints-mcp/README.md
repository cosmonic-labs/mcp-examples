# cfpb-complaints-mcp

An MCP server for the **CFPB Consumer Complaint Database** — built as a
WebAssembly component for Cosmonic Desktop. Ask questions in plain language
about **17 million real consumer complaints** against banks, credit bureaus,
debt collectors, and lenders, from December 2011 to within days of today.

> *"Which companies drew the most mortgage complaints in Texas last year, and
> is the trend up or down?"*

This example demonstrates **outbound HTTP against a large, quirky public
dataset**: no API key, one allow-listed host, and a client layer whose real job
is to keep three genuinely misleading upstream behaviors from reaching the
model as wrong answers.

Built with [mcp-server-template-rs](https://github.com/cosmonic-labs/mcp-server-template-rs):
rmcp 3.x, MCP spec 2026-07-28, exports `wasi:http/handler@0.3.0`.

---

## What the data is

Every complaint the Consumer Financial Protection Bureau forwards to a company
for response becomes a public record. Each carries the product, the issue, the
company, the consumer's state and ZIP, how it arrived, and how the company
closed it. Roughly **one in ten** also carries the consumer's own narrative,
published only with their explicit consent.

It is one of the largest public records of how financial companies actually
treat their customers — and it is updated daily.

## Tools

| Tool | Answers |
|---|---|
| `search_complaints` | *"Show me complaints about X."* Free-text plus filters, paged, narratives previewed to 600 characters. |
| `get_complaint` | *"Read that one in full."* One complaint by id, with the untruncated narrative. |
| `complaint_stats` | *"Who or what tops the list?"* Rank any facet — company, product, issue, state, resolution — over a filtered slice. |
| `complaint_trends` | *"Is this getting worse?"* Volume over time, optionally split by product, issue, company, or tags. |
| `suggest_company` | *"What does the database call this company?"* Name autocomplete. |

`search_complaints`, `complaint_stats`, and `complaint_trends` take an
**identical filter set** — company, product, issue, state, ZIP, tags, intake
channel, resolution, narrative presence, date range — so a slice worked out on
one transfers verbatim to the others. The shared arguments are generated by one
macro in `src/server.rs`, which keeps the three schemas identical by
construction.

## Use cases

**Competitive and market research.** Rank complaint volume by company within a
product line, then split it by issue to see *what* customers complain about,
not just how often. Track a competitor's trend line across a product launch.

**Due diligence.** Before signing with a servicer, lender, or fintech, pull
their complaint mix, their resolution rates (`company_response`), and whether
they answer on time (`timely`). A company closing most complaints "with
explanation" and few "with monetary relief" looks different from one that
mostly pays out.

**Consumer advocacy and journalism.** Find published narratives on a specific
practice — junk fees, escrow errors, credit-report disputes — with
`has_narrative: true` and a free-text search, then read the strongest ones in
full. Filter by `tags` to surface complaints from servicemembers or older
Americans.

**Regulatory and policy work.** Chart the national issue mix quarter over
quarter, or compare a state against the country. The 2023 recategorization of
credit-reporting products is visible directly in the trend series.

**Product and CX teams.** Read what customers say about *your own* company in
their own words, ranked and filtered, without building an ETL pipeline over a
17-million-row dataset.

> **Read the results honestly.** Complaints are consumer *allegations*. The
> CFPB does not verify them before publishing, and volume tracks a company's
> size and its customers' propensity to complain at least as much as its
> conduct — the three credit bureaus dominate every ranking largely because
> they touch everyone. Normalize before comparing companies. The server's own
> MCP instructions tell the model the same thing, so it surfaces the caveat
> rather than implying wrongdoing.

## The three upstream traps

The CFPB's search API is Elasticsearch with a thin wrapper, and it exposes
three behaviors that produce confidently wrong answers if passed through
naively. Each is handled here, surfaced in the tool descriptions, and pinned by
a test in `scripts/e2e.sh`.

**1. Facets exclude their own filter.** Every aggregation is computed with all
filters applied *except the one on its own field*. Group by `state` while
filtering `state=CA` and you get all fifty states back. So `complaint_stats`
returns both numbers, explicitly:

```json
{ "filtered_total": 922897,          // hits.total — the real count of the slice
  "facet_total": 10003219,           // what the buckets actually sum toward
  "facet_excludes_own_filter": true }
```

**2. Only one of the three date series is fully filtered.** The trends endpoint
returns `dateRangeBrush` (all of time, for the UI's range slider),
`dateRangeBuckets` (**silently drops the non-date filters**), and
`dateRangeArea` (honors everything). Under `product=Mortgage`,
`dateRangeBuckets` reported 10,003,219 where the true figure was 45,689.
`complaint_trends` uses `dateRangeArea`; the e2e suite asserts the returned
series sums to `range_total` so the wrong one cannot creep back.

**3. A categorical `lens` is a 400 without a `sub_lens`.** `lens=issue` alone
is rejected. The tool fills in a sensible second dimension when the caller
omits one, and still accepts an explicit `sub_lens`.

A fourth, smaller kindness: upstream **400 bodies are passed through intact**.
When a filter value is wrong, the model sees `{"state":{"0":["\"ZZ\" is not a
valid choice."]}}` and corrects itself on the next call, instead of a flattened
"request failed".

## Endpoints & `allowedHosts`

Everything is served from one host, so the outbound allow-list is one entry —
and egress is deny-all without it:

```yaml
allowedHosts: [www.consumerfinance.gov]
```

| Endpoint | Used by |
|---|---|
| `/data-research/consumer-complaints/search/api/v1/` | `search_complaints`, `complaint_stats` |
| `…/api/v1/{id}` | `get_complaint` |
| `…/api/v1/trends` | `complaint_trends` |
| `…/api/v1/_suggest_company/` | `suggest_company` |

No API key, no auth, no secrets. The server holds no state between requests.

## Run it

The fastest path — **nothing to build**. `deploy/workload.yaml` points at the
published image on GHCR, so Cosmonic Desktop pulls and runs it. Apply it
through the **Cosmonic Desktop UI**, the `cosmonic_apply_workload` MCP tool, or
the daemon socket directly:

```console
$ SOCK="$HOME/Library/Application Support/Cosmonic/cosmonicd.sock"
$ python3 -c "import yaml,json,sys; json.dump(yaml.safe_load(open('deploy/workload.yaml')), sys.stdout)" \
  | curl --unix-socket "$SOCK" -X POST http://localhost/v1/workloads \
      -H 'Content-Type: application/json' --data-binary @-
```

(The socket API takes JSON only — hence the conversion. The Desktop UI and the
`cosmonic_apply_workload` MCP tool both accept the YAML manifest as-is.)

It comes up at:

```
http://cfpb-complaints-mcp.localhost.cosmonic.sh:8200/
```

Confirm it's alive:

```console
$ curl -X POST http://cfpb-complaints-mcp.localhost.cosmonic.sh:8200/ \
    -H 'Content-Type: application/json' \
    -H 'Accept: application/json, text/event-stream' \
    -H 'MCP-Protocol-Version: 2026-07-28' \
    -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2026-07-28","capabilities":{},"clientInfo":{"name":"you","version":"0"}}}'

data: {…"serverInfo":{"name":"cfpb-complaints-mcp","version":"0.1.0"}…}
```

## Connect it to Claude

**Claude Code** — one command:

```console
$ claude mcp add --transport http cfpb-complaints \
    http://cfpb-complaints-mcp.localhost.cosmonic.sh:8200/
```

Check it took with `claude mcp list`, then just ask:

> *"Using the CFPB tools: what were the top five issues for auto loans in
> Florida last year, and how did complaint volume trend by quarter?"*

**Claude Desktop** — add the server to
`~/Library/Application Support/Claude/claude_desktop_config.json` and restart:

```json
{
  "mcpServers": {
    "cfpb-complaints": {
      "type": "http",
      "url": "http://cfpb-complaints-mcp.localhost.cosmonic.sh:8200/"
    }
  }
}
```

**Anything else** that speaks MCP streamable HTTP: point it at the same URL. The
server is stateless, so no session affinity is required.

## Build from source

Prerequisites: Rust 1.90+ with `rustup target add wasm32-wasip2`. The e2e suite
also needs `wasm-tools`, `wasmtime` ≥ 46, `python3`, and `curl`.

```console
$ cargo build --release        # -> target/wasm32-wasip2/release/cfpb_complaints_mcp.wasm
$ ./scripts/e2e.sh             # 54 hermetic checks, no network needed
```

The e2e suite runs the component under `wasmtime serve` against a local fixture
that impersonates the CFPB API — including its facet semantics, its unfiltered
date aggregation, and its `sub_lens` rejection — so the traps above stay fixed.

To iterate against Desktop's own registry, use `workload.yaml` instead:

```console
$ wash oci push --insecure \
    oci-registry.localhost:8200/cfpb-complaints-mcp:0.1.0 \
    target/wasm32-wasip2/release/cfpb_complaints_mcp.wasm
```

> **Bump the tag on every rebuild.** Desktop caches the local registry by tag —
> re-pushing new content under a tag it has already pulled keeps serving the
> old layer, and a stop/start does not clear it. The `serverInfo.version` in
> the `initialize` response is the quickest way to tell which build is live.
> Or pin the digest that promote returns.

## Layout

```
src/lib.rs         wasi:http@0.3.0 (WASI p3) entry point; streams rmcp's response
src/bridge.rs      the tokio <-> component-model-async bridge, and outbound HTTP
src/server.rs      the five tools, their schemas, and the server instructions
src/cfpb.rs        CFPB client: query building, response reshaping, error taxonomy
src/telemetry.rs   structured JSON logs on stderr, W3C traceparent on the span
workload.yaml      Workload for a locally built image (Desktop's registry)
deploy/workload.yaml   Workload for the published GHCR image
scripts/e2e.sh     hermetic test suite (fixture server + wasmtime serve)
```

## Notes on the data

Narratives are scrubbed by the CFPB before publication: names, dollar amounts,
and dates are replaced with `XXXX` and `{$…}` placeholders. Some records also
carry a literal `b'…'` Python bytes wrapper around the narrative text — that
artifact is in the source data, not introduced here.

Complaint counts move for reasons other than conduct: the CFPB recategorized
credit-reporting products in 2023, and third-party filing services drove a
large surge in credit-reporting complaints from 2023 onward. Both are plainly
visible in `complaint_trends` and are worth naming in any analysis.

Source: <https://www.consumerfinance.gov/data-research/consumer-complaints/>
